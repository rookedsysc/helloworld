# Jaeger, Zipkin, Loki, Tempo를 OpenTelemetry Collector와 함께 구성하는 방식

## 개요

Jaeger, Zipkin, Tempo는 모두 트레이스를 다루지만 역할과 운영 방식이 조금씩 다릅니다. Loki는 로그 백엔드입니다. 그래서 `Jaeger + Zipkin + Loki + Tempo`를 한 번에 언급할 때는 보통 다음처럼 이해하는 편이 맞습니다.

- `Jaeger`: 트레이스 저장/조회/UI
- `Zipkin`: 트레이스 저장/조회/UI
- `Tempo`: 대용량 트레이스 저장 백엔드
- `Loki`: 로그 저장/조회 백엔드
- `OpenTelemetry Collector`: 애플리케이션에서 받은 telemetry를 가공해서 여러 백엔드로 보내는 중간 계층

핵심 답부터 말하면, `OTel Collector에 붙이는 식으로 해야 하느냐?`에 대한 답은 다음과 같습니다.

- 운영 환경에서는 `대체로 예`입니다.
- 개발 환경이나 소규모 환경에서는 SDK가 백엔드로 직접 보내도 됩니다.
- 하지만 Jaeger, Zipkin, Tempo, Loki 같이 여러 백엔드를 함께 쓰거나, 배치/재시도/샘플링/민감정보 제거/팬아웃이 필요하면 Collector를 앞에 두는 구성이 가장 일반적입니다.

## 결론

### 가장 실무적인 권장 구조

```text
Application SDKs
  -> OTLP (4317/4318)
OpenTelemetry Collector
  -> traces -> Tempo
  -> traces -> Jaeger
  -> traces -> Zipkin
  -> logs   -> Loki
```

이 구조가 좋은 이유는 다음과 같습니다.

- 애플리케이션은 `OTLP`만 알면 됩니다.
- 백엔드가 바뀌어도 애플리케이션 코드를 거의 안 건드려도 됩니다.
- Collector에서 `batch`, `retry`, `queue`, `WAL`, `tail sampling`, `attribute 정리`를 공통으로 처리할 수 있습니다.
- 하나의 입력을 여러 백엔드로 팬아웃할 수 있습니다.

### 언제 직접 붙여도 되는가

- Jaeger는 OTLP를 직접 받을 수 있습니다.
- Tempo도 OTLP를 직접 받을 수 있습니다.
- Loki도 OTLP 로그 수신 endpoint를 제공합니다.
- 그래서 기술적으로는 `SDK -> backend 직접 전송`이 가능합니다.

다만 OpenTelemetry 공식 문서는 일반적으로 Collector 사용을 권장합니다. 이유는 서비스가 빠르게 telemetry를 넘기고, Collector가 재시도, 배치, 암호화, 민감정보 필터링 같은 후처리를 맡는 편이 더 유리하기 때문입니다.

## 구성 개념 정리

### 1. Jaeger와 Zipkin은 트레이스 UI/백엔드 계열

Jaeger 공식 문서에 따르면 Jaeger는 OTLP를 직접 받을 수 있고, Zipkin 포맷도 받을 수 있습니다. 즉 Jaeger는 현대적인 OTel 경로와 레거시 Zipkin 경로를 둘 다 수용할 수 있습니다.

Zipkin은 전통적인 Zipkin collector/query/web UI 구조를 가집니다. OTel Collector에서 `zipkin` exporter를 통해 Zipkin으로 전달하는 방식이 깔끔합니다.

### 2. Tempo는 트레이스 저장 백엔드에 가깝다

Tempo는 Jaeger/Zipkin처럼 자체 UI 중심 제품이라기보다, 대용량 trace 저장과 Grafana 연동에 강한 백엔드입니다. 따라서 보통은 `Tempo + Grafana` 조합으로 봅니다.

### 3. Loki는 로그 백엔드다

Loki는 traces가 아니라 logs를 저장합니다. 그래서 `Jaeger + Loki` 또는 `Tempo + Loki` 조합은 보완 관계입니다. 같은 trace/span ID를 공통 속성으로 넣어 두고 Grafana에서 로그-트레이스 상호 이동을 하게 만드는 식입니다.

### 4. Collector는 공통 ingress 계층이다

애플리케이션은 `OTLP`로 Collector에 보내고, Collector가 각 백엔드가 원하는 프로토콜로 다시 export합니다.

- Jaeger: 보통 `otlp` exporter로 연결
- Tempo: 보통 `otlp` exporter로 연결
- Zipkin: `zipkin` exporter로 연결
- Loki: `otlphttp` exporter로 `/otlp` endpoint에 연결

## 추천 아키텍처 패턴

### 패턴 A. 가장 추천: 앱 -> Collector -> 여러 백엔드

```text
App
  -> OTLP -> Collector
Collector
  -> OTLP/gRPC -> Tempo
  -> OTLP/gRPC -> Jaeger
  -> Zipkin HTTP -> Zipkin
  -> OTLP/HTTP  -> Loki
```

이 패턴은 아래 상황에서 특히 좋습니다.

- Jaeger UI도 보고 싶음
- Grafana Tempo도 같이 운영하고 싶음
- 로그는 Loki로 모으고 싶음
- 추후 Zipkin 의존 서비스도 남아 있음

### 패턴 B. 단순 개발용: 앱 -> Jaeger 또는 Tempo 직접 연결

```text
App -> Jaeger OTLP
```

또는

```text
App -> Tempo OTLP
```

개발/테스트에서는 괜찮지만, 운영으로 가면 Collector를 중간에 두는 쪽이 대체로 낫습니다.

### 패턴 C. 운영 확장형: 앱 -> Agent Collector -> Gateway Collector -> backends

노드 가까이에 Agent Collector를 두고, 중앙 Gateway Collector가 fan-out과 샘플링을 담당하는 2단 구성이 더 탄탄합니다.

## 실제 예시 코드

아래 예시는 `애플리케이션 -> OTel Collector -> Tempo/Jaeger/Zipkin/Loki` 흐름을 보여주는 예시입니다.

### 1. 애플리케이션 측 환경 변수 예시

애플리케이션은 backend를 직접 알지 않고 Collector만 바라보게 두는 편이 가장 깔끔합니다.

```bash
# 애플리케이션은 Collector만 바라본다
export OTEL_SERVICE_NAME="checkout-api"
export OTEL_EXPORTER_OTLP_ENDPOINT="http://otel-collector:4318"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"

# 필요하면 signal별 분리도 가능
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT="http://otel-collector:4318/v1/traces"
export OTEL_EXPORTER_OTLP_LOGS_ENDPOINT="http://otel-collector:4318/v1/logs"
```

### 2. `otel-collector.yaml` 예시

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 5s
    limit_mib: 512
    spike_limit_mib: 128
  batch:
    send_batch_size: 1024
    timeout: 5s
  resource:
    attributes:
      - key: deployment.environment
        value: local
        action: upsert

extensions:
  health_check:
    endpoint: 0.0.0.0:13133
  file_storage:
    directory: /var/lib/otelcol

exporters:
  debug:
    verbosity: basic

  # Tempo는 OTLP로 받는 구성이 가장 자연스럽다
  otlp/tempo:
    endpoint: tempo:4317
    tls:
      insecure: true
    sending_queue:
      storage: file_storage
      queue_size: 5000
    retry_on_failure:
      initial_interval: 5s
      max_interval: 30s
      max_elapsed_time: 10m

  # Jaeger도 OTLP 수신 가능
  otlp/jaeger:
    endpoint: jaeger:4317
    tls:
      insecure: true
    sending_queue:
      storage: file_storage
      queue_size: 5000

  # Zipkin은 zipkin exporter 사용
  zipkin:
    endpoint: http://zipkin:9411/api/v2/spans

  # Loki는 native OTLP endpoint 권장
  otlphttp/loki:
    endpoint: http://loki:3100/otlp

service:
  extensions: [health_check, file_storage]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlp/tempo, otlp/jaeger, zipkin, debug]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlphttp/loki, debug]
```

이 설정의 포인트는 다음입니다.

- 앱은 `otlp` receiver 하나만 바라봅니다.
- trace는 `Tempo`, `Jaeger`, `Zipkin`으로 동시에 fan-out 됩니다.
- log는 `Loki`로 보냅니다.
- `file_storage`를 사용해 exporter queue를 디스크에 유지할 수 있습니다.

### 3. `docker-compose.yaml` 예시

```yaml
version: "3.9"

services:
  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.149.0
    command: ["--config=/etc/otelcol/config.yaml"]
    volumes:
      - ./otel-collector.yaml:/etc/otelcol/config.yaml
      - otelcol-data:/var/lib/otelcol
    ports:
      - "4317:4317"
      - "4318:4318"
      - "13133:13133"
    depends_on:
      - tempo
      - loki
      - jaeger
      - zipkin

  tempo:
    image: grafana/tempo:2.10.0
    command: ["-config.file=/etc/tempo.yaml"]
    volumes:
      - ./tempo.yaml:/etc/tempo.yaml
    ports:
      - "3200:3200"
      - "4319:4317"

  loki:
    image: grafana/loki:3.7.0
    command: ["-config.file=/etc/loki/local-config.yaml"]
    volumes:
      - ./loki-config.yaml:/etc/loki/local-config.yaml
    ports:
      - "3100:3100"

  jaeger:
    image: jaegertracing/all-in-one:2.8.0
    ports:
      - "16686:16686"
      - "14250:14250"
      - "4317:4317"
      - "4318:4318"
      - "9412:9411"

  zipkin:
    image: openzipkin/zipkin:latest
    ports:
      - "9411:9411"

volumes:
  otelcol-data:
```

포트 충돌을 피하려면 실제 실행 시 호스트 포트는 조정해야 합니다. 예를 들어 위 예시는 컨테이너 내부에서는 `tempo:4317`, `jaeger:4317`처럼 접근하므로 Collector 입장에서는 문제가 없지만, 호스트 포트는 서로 겹치지 않게 따로 노출하는 편이 좋습니다.

## 그래서 "Collector에 붙이는 식으로 해야 하는가?"

짧게 정리하면 아래와 같습니다.

### 예, 특히 이런 경우는 Collector가 맞습니다

- 여러 backend로 동시에 보내야 함
- 앱 코드는 OTLP 하나로 통일하고 싶음
- 추후 Jaeger -> Tempo 같은 이전 가능성을 열어두고 싶음
- retry, queue, sampling, redaction, enrichment가 필요함
- logs/traces를 함께 정리하고 싶음

### 직접 붙여도 되는 경우

- 데모/로컬 개발
- backend가 1개뿐임
- Collector 운영 복잡도를 당장 피하고 싶음

### 실무 추천

- traces: `SDK -> Collector -> Tempo`를 기본으로 두기
- Jaeger가 꼭 필요하면 Collector에서 추가 fan-out 하기
- Zipkin은 레거시 호환이나 비교 목적이 아니면 굳이 새 표준으로 선택하지 않아도 됨
- logs: `SDK/agent -> Collector -> Loki`

## 선택 기준

### Jaeger를 같이 둘 만한 경우

- Jaeger UI와 익숙한 운영팀이 있음
- 기존 Jaeger 자산이 이미 많음
- OTel 이전 중이라 과도기 브리지 역할이 필요함

### Zipkin을 같이 둘 만한 경우

- 기존 Zipkin 생태계 연동이 남아 있음
- 레거시 서비스가 Zipkin 포맷을 이미 사용 중임

### Tempo + Loki 조합이 강한 경우

- Grafana 중심 운영을 하고 있음
- trace와 log를 Grafana에서 함께 탐색하고 싶음
- 대용량 trace 저장과 비용 효율을 중시함

## 주의할 점

### 1. Jaeger + Zipkin + Tempo를 모두 동시에 운영하면 중복 저장이 생깁니다

비교 검증이나 마이그레이션 단계가 아니면 보통은 trace backend를 하나의 주력으로 정합니다.

### 2. Loki는 trace backend가 아닙니다

Loki에 trace를 직접 저장하는 게 아니라, 로그 안에 `trace_id`, `span_id`, `service.name` 같은 속성을 남겨서 상호 연계하는 방식입니다.

### 3. Loki에는 `loki exporter`보다 native OTLP endpoint가 더 권장됩니다

신규 구성이라면 `otlphttp -> /otlp` 경로가 더 자연스럽습니다.

### 4. Collector는 배치/큐/WAL을 꼭 고려하는 편이 좋습니다

네트워크 문제나 backend 장애 시 유실을 줄이려면 `sending_queue`, `retry_on_failure`, `file_storage` 조합을 같이 보는 편이 좋습니다.

## 요약

가장 현실적인 답은 이것입니다.

- `예, 보통은 OTel Collector에 붙이는 식으로 구성하는 게 맞습니다.`
- `Jaeger/Tempo`는 traces backend이고 `Loki`는 logs backend입니다.
- `Zipkin`은 trace 레거시/호환 경로로 생각하면 됩니다.
- 신규 표준 기준으로는 `App -> Collector -> Tempo(+필요시 Jaeger), Logs -> Loki` 구성이 가장 무난합니다.

원하시면 다음 단계로 이어서 작성할 수 있습니다.

1. Docker Compose가 실제로 뜨도록 파일 3~4개를 바로 만들어드리기
2. Kubernetes 기준 Helm values 예시로 바꿔드리기
3. Spring Boot 또는 Node.js 앱에서 OTel SDK 설정까지 붙여드리기
